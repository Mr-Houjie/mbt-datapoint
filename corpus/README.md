# 语料

这里放的是**文件形式**的报文样本，不是代码里的字符串常量。`moon run cmd/verify` 会把它们逐条跑一遍。

换成一批现场报文，只要丢进目录，不用改一行代码——这是把它们做成文件的唯一理由。

## 目录

| 目录 | 内容 | 期望 |
| --- | --- | --- |
| `good/` | 符合标准的报文，覆盖实时/分钟/小时/日数据、参数命令、交互命令，含两条标准附录示例 | 解码成功 + 往返字节一致 |
| `edge/` | 合法但少见的形态：空数据区、分包、含中文的数据区、无密码、20 个数据项 | 同上 |
| `split/` | 分包组，文件名前缀相同的若干帧属于同一条逻辑报文 | 喂进同一台重组器后必须拼成一条完整数据区 |
| `bad/` | 各种不合法报文 | 必须被拒绝，且错误类型与文件名前缀一致 |
| `stream/` | 整段 TCP 流：正常帧 + 坏帧 + 一组分包 + 一行噪声 | 跑一遍管道后，帧数 / 拒绝数 / 数据点数与预期一致 |
| `rules/` | 规则配置（`demo.rules`） | 语法零错误；对 `edge/many-items.frame` 必须命中期数量的错误 |
| `cipher/` | **加密报文原始字节**：按 HJ 212-2025 附录 A.2 示例 2 逐字节还原（307 字节，数据区 208 字节 = 13 组密文） | `mbt-datapoint cipher ... --key <16个0x30>` 必须解出示例 1 的 13 项并转成数据点；不配组件时必须报 `CipherRequired` |

`bad/` 的文件名形如 `BadCrc__校验码被改动.frame`。`__` 之前是期望的 `DecodeError::kind()`，之后是说明。自检会拿它做断言——这样"我以为它会报错"就变成了可执行的检查。

`split/` 的前缀用法一样：`split-3__p1.frame`、`split-3__p2.frame`、`split-3__p3.frame` 同属 `split-3` 这一组。文件名里的 `p1/p2` 只用于排序，真正的包号在报文体的 `PNO` 字段里。`split-3` 的第三包故意让分包边界落在一个中文字段上（`Info=备用通道`），长度字段按字符算就会拼不上，按字节算才对。

`stream/` 是一条混合流的原始字节，用来验证「整段流跑完，计数对不对」。它把正常帧、CRC 被改的坏帧、一组分包、一行噪声拼在一起——这正是现场抓包的样子。期望值写死在 `cmd/verify` 的调用处，数字对不上就立刻失败，而不是从文件名里猜。

`rules/` 放的是文本规则配置，与代码无关。量程该设多少、哪些状态码算合法，是现场的事；`demo.rules` 只是把这套语法的四类规则各写了一遍。改它不需要重新编译。

`cipher/` 里的帧是**二进制**，`0x26 0x26`（`&&`）也可能出现在密文中间，所以它不走明文语料那条自检路径，而是由 `mbt-datapoint cipher` 直接按字节读。密钥是标准附录 A.2 用的 16 个 `0x30`：

```bash
mbt-datapoint cipher corpus/cipher/a2-example2.frame --key 30303030303030303030303030303030
```

`.gitattributes` 把 `*.frame` 标成 `binary`，否则 Git 会在检出时把包尾的 `\r\n` 归一化，密文的长度和 CRC 全都会变——这类文件必须逐字节原样传输。

## 生成方式

```bash
python corpus/generate.py
```

`generate.py` **不复用** MoonBit 实现，而是用 Python 重写了一遍 CRC16（附录 A 的写法）。如果两套实现算出的校验码不同，生成阶段就会暴露出来。这算是给校验码加了一道独立对拍。

脚本开头还有一道自检：按它的 CRC 算两条官方附录示例的数据段，结果必须分别是 `2017 → 0x1C80`、`2025 → 0x2200`，任一不符就直接退出。这条断言比任何文档都管用——算法一旦被改错，语料根本生成不出来。

## 标准附录 A 的示例报文

两条，分别来自 2017 与 2025 两个版本，都是从标准原文逐字符照抄，校验码未作任何改动：

```
##0101QN=20160801085857223;ST=32;CN=1062;PW=100000;MN=010000A8900016F000169DC0;Flag=5;CP=&&RtdInterval=30&&1C80
##0087QN=20240601085857223;ST=32;CN=1011;PW=123456;MN=010000A8900016F000169DC0;Flag=9;CP=&&&&2200
```

| 文件 | 版本 | 数据段长度 | 校验码 |
| --- | --- | --- | --- |
| `good/appendix-a__标准附录A示例.frame` | HJ 212-2017 附录 A | 101 字节 | `1C80` |
| `good/appendix-a-2025__标准附录A示例.frame` | HJ 212-2025 附录 A.1 | 87 字节 | `2200` |

它们是本库与标准对齐的**锚点**：长度字段、数据段字节数、CRC 三者都对得上，才能说明长度计数、CRC 算法、字段顺序三件事同时理解正确。两条都用 `cmp` 与标准原文核对过字节。`moon run cmd/verify` 每次都会跑它们。

第二条还顺带盯住版本位：`Flag=9` 的低六位是 `001001`，`V5–V0` 为 `000010`，正是 HJ 212-2025 的版本编码。

需要注意 CRC 算法的差异：附录 A 的每字节入口是 `crc = (crc >> 8) ^ byte`，而 CRC-16/MODBUS 是 `crc ^= byte`，初值和多项式相同但结果完全不同。同一段 2017 数据段用 MODBUS 算得 `0759`。曾经的实现就是套了 MODBUS，于是把这两条标准示例都判成了坏帧。

## 命令码与系统编码

语料里的 `CN`、`ST` 取值逐条对照标准正文的命令表与系统编码表（2017 版为表 9 与表 5）：

- `ST=31` 大气环境污染源，`ST=32` 地表水体环境污染源（水质），`ST=51` 烟气排放过程监控；
- `CN=2011` 污染物实时数据，`2051` 分钟数据，`2061` 小时数据，`2031` 日数据，`2041` 设备运行时间日历史数据。

注意 `32` 是水质不是烟气——这是最常见的误记之一，代码里有回归测试盯着。
