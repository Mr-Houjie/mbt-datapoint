# mbt-hj212

HJ 212 污染物在线监控数据传输协议的 MoonBit 实现：帧编解码、数据区解析、命令层、流式分帧，附带一个能把一条原始报文摊开成字段表的命令行工具。

核心库零依赖，只用 MoonBit 标准库。

```
##0140QN=20240115103000123;ST=31;CN=2011;PW=123456;MN=0100...DC0;Flag=5;CP=&&DataTime=...;a34013-Rtd=1.52&&3647\r\n
└┬─┘└──┘└──────────────────── 数据段 ────────────────────┘└──┘└─┘
包头 长度                                                 CRC  包尾
```

## 为什么值得单独做一个

HJ 212 是国内污染源在线监测联网的强制标准，全国每一台数采仪都在按它往生态环境部门的平台报送数据。协议本身不难，难的是它有三处地方特别容易实现错，而且错了不会报错，只会静默丢数据：

1. **长度字段按 UTF-8 字节数算，不是字符数。** 数据区里出现一个中文（比如 `Info=备用通道`），按字符数算就会少 6 个字节，接收端随之错位到 CRC，整帧被丢。这个库里长度、CRC 共用同一套字节计数。
2. **`CP` 的取值自己也用 `;` 分隔字段。** 把数据段直接按 `;` 切开再找 `CP`，数据区会被撕成碎片。必须先定位 `CP=`，之前的按 `;` 切字段，之后的整体交给数据区。
3. **TCP 是字节流，粘包半包是常态。** 一次 `read` 可能拿到两条半报文，也可能只拿到 `##01`。分帧器必须能跨 `read` 保持状态。

这三条都有对应的测试和语料，不是靠注释声明的。

## 用法

### 解码一条报文

```moonbit
match @hj212.Frame::decode(raw) {
  Ok(frame) => {
    println(frame.segment.cn)              // "2011"
    println(frame.segment.cp.get("a34013-Rtd"))  // Some("1.52")
  }
  Err(error) => println(error.message())   // 直接给人看的中文描述
}
```

错误分两类，刻意分开：

- `Frame::decode` 只管**结构**——包头、长度、CRC、包尾。任何一项不对就拒绝整帧，绝不"尽力而为"地猜。
- `Segment::validate` 只管**语义**——MN 长度与版本是否匹配、Flag 声明分包却没带 PNUM/PNO 之类。这些不影响解码，只作为提示返回。

`DecodeError::kind()` 给出稳定的错误标识（`"BadCrc"`、`"Truncated"`……），适合写日志或做分支；`message()` 是给人看的中文描述。

### 流式分帧

```moonbit
let framer = @hj212.Framer::new()
for chunk in chunks {
  for event in framer.feed(chunk) {
    match event {
      @hj212.Good(frame) => handle(frame)
      @hj212.Bad(error, raw) => log(error, raw)
      @hj212.Noise(text) => ()          // 日志前缀、半包残片
    }
  }
}
```

`feed` 返回的是数组，一次喂入可能吐出多条帧。不足一帧的部分留在 `framer.pending()` 里等下一次。

### 构造报文

```moonbit
let frame : @hj212.Frame = {
  segment: {
    qn: "20240115103000123",
    st: "31",
    cn: "2011",
    pw: "123456",
    mn: "010000A8900016F000169DC0",
    flag: @hj212.Flag::new(@hj212.V2017, false, true),
    pnum: None,
    pno: None,
    cp: @hj212.DataArea::new()
      ..set("DataTime", "20240115103000")
      ..set("a34013-Rtd", "1.52"),
    extra: [],
  },
}
println(frame.encode())
```

`encode` 会重新生成数据段（而不是复用输入原文），所以输出是规范形式：字段顺序固定、`&&` 包装一定存在、CRC 与长度一定自洽。

## 命令行

```
mbt-hj212 explain <报文|文件>     逐字段解释一条报文
mbt-hj212 check   <报文|文件>     只校验，不合法时退出码 1
mbt-hj212 frames  <报文|文件>     按 TCP 流分帧，逐条列出
mbt-hj212 encode  [选项]          构造一条报文
mbt-hj212 crc     <数据段>        算数据段的 CRC 与字节长度
```

`explain` 是最好用的一个，它把一条报文摊成表，每一行都标出来源：

```
$ mbt-hj212 explain '##0140QN=20240115103000123;ST=31;CN=2011;PW=123456;MN=010000A8900016F000169DC0;Flag=5;CP=&&DataTime=20240115103000;a34013-Rtd=1.52;a34013-Flag=N&&3647'

长度    140 字节（数据段）
CRC     3647                          校验通过
版本    HJ 212-2017
Flag    5                             版本位 000001 · 不分包 · 需应答
QN      20240115103000123             2024-01-15 10:30:00.123
ST      31                            大气环境污染源
CN      2011                          污染物实时数据 · 双向
PW      123456
MN      010000A8900016F000169DC0      24 位
CP      3 项
  DataTime          20240115103000
  a34013-Rtd        1.52
  a34013-Flag       N
```

命令行直接粘报文时末尾的 `\r\n` 常被终端吃掉，`explain`/`check`/`frames` 会自动补一次；库层保持严格，不做这种妥协。

## 语料自检

```bash
moon run cmd/verify
```

`corpus/` 下的帧是**文件**，不是代码里的字符串常量。自检会：

1. 合法帧必须能解码，且长度、CRC 与算法一致；
2. 解码再编码必须与原文件字节相同（往返一致）；
3. 非法帧必须被拒绝，且**错误类型要与文件名前缀一致**（`BadCrc__xxx.frame` 就必须报 `BadCrc`）。

第 3 条是这个命令的价值所在。它把"我以为它会报错"变成了可执行断言。开发过程中它抓出了两个真实缺陷——重复字段被静默接受、缺少 `&&` 包装的 `CP` 被当成合法数据区。

语料由 `corpus/generate.py` 生成。这个脚本**不复用** MoonBit 实现，而是用 Python 重写一遍 CRC16/MODBUS，让校验码来自一套独立实现。两边算得不一样，生成阶段就会暴露。

## 适用范围与已知偏差

**关于标准附录的 CRC 示例。** HJ 212-2017 附录 A 的示例报文，数据段是 `QN=20160801085857223;...;CP=&&RtdInterval=30&&`，标注的校验码是 `1C80`。按附录 A 自己给出的算法（初值 `0xFFFF`、反向多项式 `0xA001`、无最终异或）算同一段，得到的是 `0759`。穷举初值、多项式、正向/反向、最终异或、多种子串切片都无法得到 `0x1C80`。判断是示例沿用了旧稿。

本库以**算法**为准，因此会拒绝 `1C80` 并报出正确值 `0759`。这一条写在测试里（`标准附录示例的校验码与算法不一致`），不是悄悄绕过。

**命令表与系统编码表。** 逐条对照 HJ 212-2017 表 9 与表 5 录入，没有采用现场口头叫法。例如 `2011` 是「污染物实时数据」（取与上传共用同一码），`2041` 是「设备运行时间日历史数据」而不是又一个「日数据」；`ST=32` 是「地表水体环境污染源」（水质），烟气是 `ST=31`，烟气工况是 `ST=51`。这三处都是常见误记，代码里有专门的回归测试盯着。

**版本号。** `Flag` 的 V5–V0 位：`000000` 是 HJ/T 212-2005，`000001` 是 HJ 212-2017，`000010` 是 HJ 212-2025。注意 2017 与 2025 两次修订把最后两位的**字母**换过名（2017 写作 D=分包、A=应答，2025 写作 A=分包、D=应答），位权没变。本库只按位权判断，不引用字母。

**没有做的部分。** 监测因子编码表（附录 B，水/气各数百项）没有收录——那是查表数据而不是协议逻辑，塞进库只会让包变大。数据区里的因子名按不透明字符串处理，`DataArea::get("a34013-Rtd")` 照样能用。

## 项目结构

```
types.mbt        公共类型：Version、Flag、DecodeError、Segment、Frame
text.mbt         字符/字节工具：UTF-8 计数、十六进制、显示宽度对齐
crc.mbt          CRC16/MODBUS
field_type.mbt   数据类型表：C4、N5、N14.2、YYYY/MM/DD/hh/mm/ss/zzz
data_area.mbt    数据区：&& 包装、名称=值、逗号分隔多值
segment.mbt      数据段：字段切分（先定位 CP=）、序列化、语义校验
time.mbt         QN 时间戳
frame.mbt        帧编解码 + 流式分帧器
commands.mbt     命令码表（表 9）
explain.mbt      逐字段解释，供 CLI 使用
corpus/          语料与生成脚本
cmd/main/        命令行
cmd/verify/      语料自检
```
